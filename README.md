# Кандидатогенерация объявлений услуг Авито

## Что делает решение

По тексту запроса и его признакам выбирает 50 различных объявлений из `benchmark_items.parquet`. Выдача записывается в CSV с двумя колонками: `query_id,answer`. Идентификаторы не преобразуются и не сокращаются. Хардкода по `query_id` нет.

Внешние API, внешняя разметка, готовые решения других участников и предобученные нейросетевые модели не используются. Для обучения нужны только три исходных файла задания. После установки зависимостей весь расчёт выполняется локально на CPU.

## Метод

1. Нормализация текстов: нижний регистр, замена `ё` на `е`, выделение русских и латинских слов и чисел, русский Snowball-стемминг. Он сводит многие словоформы к общей основе. HTML и Unicode-обфускация отдельно не обрабатываются.
2. Раздельные индексы BM25 для заголовка, описания и параметров объявления. Описание ограничено первыми 7 000 символами. Общий словарь ограничен 220 000 терминами. Частота термина насыщается по формуле BM25, длина документа нормализуется.
3. TF-IDF по символьным n-граммам длины 3–5 в заголовках. Это дополнительный канал для опечаток, частей слов и близких написаний; он не гарантирует семантического понимания.
4. Обучение по истории положительных пар. Для нового запроса находятся 35 похожих обучающих запросов по словесному и символьному TF-IDF. Их сходства возводятся в восьмую степень и нормализуются. По их выбранным объявлениям оцениваются вероятности микрокатегорий, строится расширение запроса названиями объявлений и учитывается история выбора конкретных `item_id`.
5. География: совпадение локации, расстояние до медианного центра локации, частота переходов из локации поиска в локацию объявления. Идентификаторы локаций используются только как ключи; арифметика над ними не выполняется. География учитывается мягко, без обязательного отсечения других городов.
6. Объединение нескольких выдач: 300 кандидатов гибридного поиска, 130 лексических без географического усиления, 100 символьных с географией, 160 по расширению запроса и 50 по истории. После удаления повторов остаётся не более 740 кандидатов. Веса и размеры этих списков являются фиксированными эвристиками.
7. CatBoost оценивает кандидатов по 27 числовым признакам, после чего остаются 50 лучших. Это внутренний обучаемый отбор кандидатогенератора; дальнейшее продуктовое ранжирование в рамках задания не реализуется. В признаки входят текстовые сходства, география, соответствие фильтрам, цена, рейтинг, отзывы и обучающая история.

Флаг `search_is_delivery_search` входит в описание контекста при разбиении, но отдельным признаком модели не используется: во всех запросах бенчмарка он равен нулю. Тексты, локация, категория и текстовые фильтры участвуют в поиске.

Рейтинг и параметры используются как мягкие признаки. Например, фильтр «4 звезды и выше» не превращается в жёсткое условие: это оставляет шанс объявлениям с неполными или несогласованными признаками.

## Валидация и ограничения оценки

В `train` только положительные пары. Из них для проверки используются пары, чьи объявления присутствуют в корпусе бенчмарка. Это позволяет считать Recall@50 на полном корпусе из 189 212 объявлений, не добавляя в него искусственные документы.

Для разбиения выбираются 4 000 нормализованных текстов запросов. Редкие запросы получают больший шанс попасть в выборку. Для каждого текста случайно выбирается один наблюдавшийся контекст: локация, фильтры, категория и флаг доставки. Все известные положительные объявления этого контекста образуют разметку.

Все строки выбранных текстов исключаются из истории. Дополнительно для 90% уникальных положительных объявлений проверки из истории удаляются все пары с ними, включая другие запросы. Это имитирует преимущественно новые объявления. Видимые тексты корпуса остаются доступны: индексирование документов без их меток допустимо для поиска.

Разбиение: 2 400 запросов для обучения CatBoost, 800 для ранней остановки, 800 для контрольной оценки. Параметры генератора фиксированы. Контрольная часть не используется для ранней остановки. Seed: 20260927.

Ненаблюдавшиеся пары среди найденных кандидатов используются как отрицательные примеры, хотя некоторые из них тоже могут быть релевантными. Поэтому вероятности CatBoost нельзя интерпретировать как откалиброванную вероятность релевантности. Положительные объявления, которые генератор не нашёл, не добавляются искусственно: это сохраняет честную оценку полноты всего каскада.

Эта проверка состоит из новых текстов запросов и не полностью повторяет распределение бенчмарка. В частности, у бенчмарка есть и знакомые запросы, а состав категорий отличается. Указанные значения — локальные метрики, а не результат скрытого теста.

После валидации признаки истории для предсказания перестраиваются по полному `train`. Число деревьев выбирается по отложенной части, затем модель отбора переобучается на всех 4 000 размеченных запросах из train. Метрики вычислены до этого финального переобучения. Это даёт некоторый сдвиг распределения признаков; скрытое качество можно определить только проверкой организатора.

## Итоговый файл

Сформирован `answer.csv`: 2 452 строки, ровно 50 уникальных кандидатов в каждой. Проверены точное покрытие query_id, регистр и длина идентификаторов, отсутствие лишних колонок и принадлежность всех item_id корпусу. Отчёт проверки и SHA-256 результата находятся в `output_validation.json`. Исходные Parquet не включены в архив; их контрольные суммы записаны в `input_checksums.json`.

## Полученный результат локальной проверки

| Метод | Recall@50, dev (800 запросов) | Recall@50, контроль (800 запросов) |
|---|---:|---:|
| Лексические признаки и география | 0,8156 | 0,8388 |
| Гибридная формула | 0,8588 | 0,8719 |
| CatBoost поверх объединённых кандидатов | **0,9000** | **0,9200** |

Полнота расширенного набора до сокращения до 50: 0,9613 на dev и 0,9706 на контроле. Модель сохраняет около 94,8% найденных на контрольной части положительных объявлений. Выбрано 496 деревьев. Полные результаты и важности признаков сохранены в `metrics.json`.

Бенчмарк не размечен, поэтому его Recall@50 здесь не заявляется. Файл `answer.csv` должен быть проверен системой организатора; доступные попытки отправки не использовались.

## Запуск

Рекомендуется Python 3.12, несколько CPU-ядер и около 8 ГБ свободной оперативной памяти. При подготовке решения использовалось окружение с приблизительно 10 ГБ RAM. Для комфортного повторного запуска лучше 16 ГБ RAM. GPU не требуется. Индексы и промежуточные признаки занимают дополнительное место на диске.

Положите исходные файлы в папку `upload` рядом со скриптами:

```text
upload/train.parquet
upload/benchmark_queries.parquet
upload/benchmark_items.parquet
```

Установите зависимости из `requirements.txt`. Они открытые и должны быть заранее установлены, если запуск проводится полностью без сети.

```bash
python -m pip install -r requirements.txt
python retrieval.py --mode prepare --data upload --work work
python retrieval.py --mode fit --work work
python retrieval.py --mode predict --data upload --work work --output answer.csv
python validate_answer.py --data upload --answer answer.csv
```

`prepare` строит индексы, разбиение и признаки. `fit` обучает модель и записывает метрики. `predict` возвращает полную разрешённую историю и формирует результат. Подготовка индексов и признаков — самая продолжительная часть; расчёт не заявляется как оптимизированный промышленный поиск с низкой задержкой.

В архив включена обученная модель `model.cbm`. Для её использования после `prepare` скопируйте её в `work/model.cbm` и запустите `predict`. Для воспроизведения обучения выполняйте все команды выше. Индекс в pickle создаётся локально; не загружайте pickle из недоверенных источников.

## Open-source компоненты

- NumPy и SciPy: векторы, разреженные матрицы и вычисления.
- pandas и PyArrow: Parquet и CSV.
- scikit-learn: CountVectorizer, TfidfVectorizer, нормализация.
- NLTK: русский SnowballStemmer, без скачивания языковых корпусов.
- CatBoost: градиентный бустинг для финального отбора.
- BM25, TF-IDF, символьные n-граммы и расширение запроса по обучающим соседям: классические методы информационного поиска; реализация объединения каналов и признаков написана для этого задания.

Версии зафиксированы в `requirements.txt`. При иной платформе возможны незначительные расхождения численного результата.
